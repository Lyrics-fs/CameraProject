# 双变量伪彩色映射技术方案（亮度 + 对比度/噪声）

## 1. 背景与问题

当前项目的伪彩色主要是将像素“亮度（灰度）”映射为颜色（例如蓝→青→绿→黄→红），因此图中颜色的物理含义主要集中在一个维度上。

在实际亮度可视化/分析中，除了亮度以外，以下信息同样重要：

- **对比度**：能反映纹理丰富度、边缘/细节强弱，常用于判断是否存在结构性信息或曝光/对焦导致的细节变化。
- **噪声水平**：在低照度或高 ISO 下更显著，噪声会影响 BV/亮度推导稳定性，也能帮助诊断“为什么某些区域看起来不靠谱”。

如果能在同一张图上同时表达“亮度 + 结构/噪声强度”，可显著提升可视化分析价值。

## 2. 目标

引入**双变量伪彩色**编码方式，使得：

1. **色相（Hue）**编码物理量 A：建议使用“亮度（或 L/BV 相关量）”
2. **饱和度（Saturation）或明度（Value）**编码物理量 B：建议使用“对比度”或“噪声水平”

这样用户可以在一张伪彩色图上同时观察：

- 哪些区域更亮/更暗（Hue）
- 哪些区域更“有细节/对比强”或更“噪声重”（S 或 V）

## 3. 方案总览（推荐编码：Hue=亮度，S=对比度/噪声）

### 3.1 物理量定义

定义每个像素位置的基础量：

- `Y`：像素亮度（可用灰度或 Y' 近似，例如 `0.299R + 0.587G + 0.114B`）

在此基础上定义辅助量 B：

1. **对比度（Contrast）**（建议优先）
   - 使用局部统计量刻画纹理/边缘强度
   - 最小可用：局部方差或局部梯度能量（例如 Sobel 梯度幅值）
   - 目标：得到范围稳定的 `C`（归一化到 0~1）

2. **噪声水平（Noise）**（可选增强）
   - 在不引入多帧累积的前提下，使用高频分量/拉普拉斯能量近似
   - 例如对亮度做小尺度平滑后，残差的能量越大则噪声越高
   - 目标：得到范围稳定的 `N`（归一化到 0~1）

### 3.2 颜色映射（HSV/HSB 双通道编码）

推荐颜色映射：

- `Hue = mapBrightness(Y)`：将亮度（或 BV→L 的对数空间）映射到色相轴
- `Saturation = mapSecondVariable(C or N)`：将对比度或噪声强度映射到饱和度
- `Value = 1.0`（或轻微跟随亮度）：保证整体可读性

最终输出：

`RGB = HSVtoRGB(Hue, Saturation, Value)`

### 3.3 可视化图例（二维表达）

当前图例是单轴（亮度 L 的色条）。双变量后建议做二维图例：

- 一条**色相条**：表示 Hue 对应的亮度范围（仍保持蓝→红或你现有的伪彩色风格）
- 一条**饱和度条/透明度条**：表示 Saturation 对应的对比度或噪声范围

二维图例的两种实现：

1. **简化版**：同时给出两个独立标尺（Hue 标尺 + Saturation 标尺），用文字提示二维编码关系
2. **增强版**：绘制小矩阵/热力图（横轴 Hue、纵轴 Saturation/噪声），每个单元格颜色代表编码结果

最小可用建议从简化版开始，避免图例过复杂。

## 4. 实现路径拆分（实时预览 vs 离线拍照图）

项目目前存在两条伪彩色链路：

- **实时预览端**：`CameraRenderer`（OpenGL ES shader，使用 `GL_OES_EGL_image_external` 纹理）
- **拍照离线端**：`CameraModel.createPseudoColorImage()`（CPU 逐像素处理 + 旋转 + 图例/统计叠加）

建议按实现难度采用“差异化策略”：

### 4.1 预览端（CameraRenderer）——轻量级局部计算

预览端 shader 需要尽量轻量，推荐：

- 仍使用 `Y` 做亮度 → Hue
- 对 B（对比度/噪声）用一个较小的局部核（例如 3x3）近似
- 将 B 做归一化（需要在 shader 中实现或以合理经验常数近似）

实现方式建议：

1. 亮度 `Y`：直接由外部纹理采样后计算灰度
2. 对比度 `C`：对 3x3 范围采样得到 `Y_i`，计算：
   - `C = stddev(Y_i)` 或 `C = max(Y_i) - min(Y_i)`（更便宜）
3. 噪声 `N`：做简化高频近似：
   - `N = abs(Y - blur(Y))`（blur 可用 3x3 均值近似）

注意：

- 由于预览端不一定具备标准导数函数（取决于设备），建议用“显式多采样核”而非依赖 `dFdx/dFdy`。
- 外部纹理是否对偏移采样支持取决于实现，但通常 `texture2D` 对 `samplerExternalOES` 允许采样；仍需在真机验证性能。

### 4.2 离线端（CameraModel）——更准确的局部统计

离线端可以承受更复杂计算（因为用户主要关心结果图质量）：

- `C`：使用局部窗口计算方差/梯度能量
- `N`：使用高频残差（例如 Laplacian energy）或 `Y - gaussianBlur(Y)` 的绝对值/能量
- 对 B 做鲁棒归一化（例如使用全图百分位裁剪到 `[p5, p95]` 再归一化）

离线端可额外做：

- 对不同亮度区间的 B 做自适应归一化（避免“暗区噪声天然更高”导致饱和度完全压扁）

--- 

## 5. 关键细节：归一化与稳定性（决定“看起来好不好”）

双变量映射最容易遇到的问题是：B 的数值范围可能随曝光/场景变化剧烈，导致饱和度区间失真。

建议以下稳定化策略：

1. **归一化方式**
   - 方案 A（最小可用）：使用固定阈值 `B_min/B_max`，将 B clamp 到 `[0,1]`
   - 方案 B（增强）：使用全图统计进行归一化（离线端推荐）
   - 方案 C（鲁棒）：使用百分位裁剪（离线端推荐），例如 p5/p95

2. **避免饱和度过度饱和**
   - 可对 `S` 做 gamma：`S = pow(S, 0.6)`（或根据实测调整）

3. **对比度/噪声的选择**
   - 对比度往往更直观、更抗“噪声占比变化”
   - 噪声水平更适合诊断低照度质量，但对曝光变化敏感

因此建议默认使用“对比度”，噪声作为切换项。

## 6. 数据流与接口改造建议（不改变现有主流程）

当前主流程在拍照后调用：

- `CameraPresenter.createPseudoColorImage()` -> `CameraModel.createPseudoColorImage()`

建议新增参数/配置对象：

- `PseudoColorMode`（例如：`LUMINANCE_ONLY`, `BRIGHTNESS_CONTRAST`, `BRIGHTNESS_NOISE`）
- `ContrastMetric` 或 `NoiseMetric`（可作为内部枚举）

并做两处接入：

1. `CameraRenderer`：新增 shader uniform（例如 `uSecondVariableType`、`uSecondMinMax`）
2. `CameraModel.createPseudoColorImage()`：新增用于 B 计算与 HSV 映射的分支

UI 层建议最小改动：

- 在界面中提供一个下拉/按钮切换伪彩色模式（若暂不做 UI，可先用默认模式对比验证）

## 7. 验证方法（如何证明方案更有价值）

建议使用以下对比验证：

1. 同一场景，不同曝光/ISO 下对比：
   - 亮度变化是否能由 Hue 清晰反映
   - 对比度/噪声变化是否能由 Saturation 体现（例如暗区噪声更明显，纹理更强区域更饱和）
2. 与单变量伪彩色对比：
   - 双变量图是否更容易定位“细节丢失/噪声增强”的区域
3. 统计一致性（可选）：
   - 看双变量图上“低饱和度/高噪声区域”是否对应 BV 推导误差更大区域（如果你有误差度量）

--- 

## 8. 推荐落地顺序（最小可用版）

1. 仅实现 **离线端** 双变量（CameraModel）：
   - Hue：沿用当前灰度→伪彩色映射风格
   - S：先实现对比度（局部方差或 max-min）
   - 添加简化图例（Hue 标尺 + Saturation 标尺）
2. 在确认效果后，再实现 **预览端**（CameraRenderer）的轻量近似：
   - shader 内完成 B 的 3x3 采样近似
3. 最后扩展噪声指标与 UI 切换

这样能最大化减少一次性风险，并尽快看到视觉增益。
